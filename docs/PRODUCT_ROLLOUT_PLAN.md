# CarryMem 产品推进方案

**版本**：v1.0  
**日期**：2026-10-11  
**状态**：执行中  
**负责人**：CarryMem Team

## 1. 原始目标

CarryMem 的目标不是继续堆积功能，而是验证并完成这条真实用户闭环：

```text
用户看懂
→ 用户装好
→ 用户验证成功
→ 用户信任记忆
→ 用户持续使用
→ 用户愿意推荐
```

本方案同时验证：

1. Hindsight 的启发是否已经落地。
2. 原有架构缺陷是否已经修复。
3. 技术债是否有明确状态和验证证据。
4. 功能是否经过生产路径、集成测试、E2E 和用户可观察结果验证。
5. 产品是否值得从小范围验证进入推广。

## 2. 产品第一阶段定位

### 核心用户

同时使用两个或多个 AI 编程客户端，并且不想反复说明编码偏好的个人开发者。

### 核心价值

> CarryMem 让你的编码偏好跨 AI 工具保持一致。

### 第一阶段范围

- 个人记忆。
- 本地优先存储。
- MCP 客户端接入。
- 跨客户端写入、召回、修改和删除。
- 可解释、可控、可恢复。

### 暂不作为第一阶段主卖点

- 企业云服务。
- 完整团队治理。
- 通用 AI 记忆平台。
- 未完成真实验收的客户端。
- 未有版本化证据的 benchmark 数字。

## 3. 已完成证据

### TRAE 与 Workbuddy

2026-10-11 已完成本机真实同步验证：

1. 两个客户端使用同一 CarryMem MCP 服务。
2. 两个客户端使用同一个 SQLite 数据库。
3. 在一个客户端写入记忆。
4. 在另一个客户端召回记忆。
5. 跨客户端同步结果正确。

这项证据证明核心跨客户端链路可用，但不等于所有 MCP 客户端都已完成验收。

### 工程和发布基础

- 核心 CI、Docker Build、Ubuntu 和 macOS 全量测试已通过。
- MCP stdio、HTTP、SSE、SQLite 并发和超时生命周期已有自动化证据。
- 依赖安全告警已处理，Dependabot 当前不作为阻塞项。
- 真实 VSCode UI 验收按用户决定暂缓。
- 技术债继续记录在 [TECH_DEBT_PLAN.md](TECH_DEBT_PLAN.md)。

## 4. 推进阶段

### 阶段一：产品定位

**状态**：第一轮完成，继续通过用户测试校验。

**本轮证据**：中英文 README、安装指南和快速开始已完成第一轮事实修正；CLI `version`、隔离环境 `doctor` 和文档静态扫描通过。

**目标**：让用户在 10 秒内理解 CarryMem 解决什么问题。

**工作**：

- README 首屏只突出个人开发者和跨 AI 工具记忆。
- 将团队规则、企业和高级架构内容下移。
- 建立“已自动配置 / 需手动配置 / 已真实验收 / 待验收”兼容性矩阵。

**退出条件**：

- 中英文 README 的核心定位一致。
- 不再使用未经验证的“所有 AI 工具都支持”表述。
- Workbuddy 状态明确为“可手动配置，跨客户端同步已验收”。

### 阶段二：首次成功体验

**状态**：第一轮文档流程完成；自动配置路径发现并修复了 MCP 数据库绝对路径问题；客户端真实对话验收继续执行。

**目标**：用户在一个短流程内完成安装、配置、写入和召回。

**标准流程**：

```bash
pip install carrymem
carrymem init
carrymem setup-mcp --all --global
carrymem doctor
```

然后在客户端对话框中：

```text
请调用 CarryMem 的 health_check，检查服务是否正常。
请记住：我偏好使用 Python 和 SQLite。
```

重新打开一个对话：

```text
请查询 CarryMem，告诉我记住了哪些编程偏好。
```

**工作**：

- 文档明确区分 CLI、MCP 和对话框的职责。
- 说明 `setup-mcp --all` 只配置已内置支持的客户端。
- 增加 Workbuddy 手动 MCP 配置说明。
- 将 `doctor` 和 `health_check` 纳入首次成功流程。
- 补充数据库路径、权限和损坏后的安全处理说明。

**退出条件**：

- 用户可以独立完成首次写入和新会话召回。
- 失败信息包含可执行的下一步。
- 至少完成 TRAE 和 Workbuddy 的真实路径验证。

### 阶段三：记忆可信和可控

**状态**：当前可交付闭环完成。MCP 已增加 `update_memory` 和 `get_memory_history`；修改、版本历史和删除已有生产路径与 E2E 证据。导出/导入已有 API 和 E2E 证据。记忆级“暂停”尚无统一 API，暂不作为已支持能力宣传，已登记为 TD-078。

**本轮证据**：MCP 工作流、MCP 工具契约和 handler 测试共 178 passed；CRUD、版本历史、导出恢复和偏好替代 E2E 共 67 passed。

**目标**：用户知道记住了什么、为什么记住、何时生效，并能控制它。

**必须验证**：

- 查看记忆、来源、作用域、状态和时间。
- 修改后旧偏好不再作为当前偏好返回。
- 删除后不能继续召回。
- 个人、项目和团队范围隔离。
- 敏感信息处理有明确结果。
- 导出和恢复有完整性校验。

**退出条件**：

- 查看、修改、版本历史、删除和导出恢复都有生产路径和 E2E 证据。
- 文档能给出普通用户可执行的查看、修改和删除方法。
- 记忆级暂停能力单独记录为未完成项，不与规则暂停混淆。

### 阶段四：三类客户端兼容性验证

**状态**：按用户决定跳过第三客户端真实验收。TRAE 与 Workbuddy 跨客户端同步已完成；其他支持本地 stdio MCP 的客户端仅作协议级可行性判断，不计入真实客户端验收数量。

**第一批客户端**：

1. TRAE：已完成。
2. Workbuddy：跨客户端同步已完成；客户端级证据继续归档。
3. Cursor 或 Claude Code：按用户决定跳过，不作为当前推广门禁。

**每个客户端必须记录**：

- 配置方法。
- 启动方式。
- 工具发现结果。
- `health_check` 结果。
- 写入结果。
- 新对话召回结果。
- 删除结果。
- 已知限制。

**退出条件**：

- 本轮记录 TRAE 与 Workbuddy 的真实验收结果；第三客户端真实验收按用户决定跳过。
- 其他客户端只记录 MCP 协议级可行性，不计入真实客户端数量。
- 每个客户端的宣传状态不超过实际证据范围。

### 阶段五：README 和演示重做

**状态**：第一轮完成。README、中文 README、安装指南和快速开始已统一 MCP 首次成功流程、33 个工具事实、TRAE/Workbuddy 真实证据和第三客户端跳过边界。

**目标**：把工程能力压缩为可理解、可安装、可验证的产品入口。

**README 顺序**：

1. 一句话价值。
2. 60 秒跨客户端演示。
3. 适合谁。
4. 三步安装。
5. TRAE 和 Workbuddy 配置。
6. `doctor`、`health_check` 和对话验证。
7. 数据位置和隐私。
8. 兼容性矩阵。
9. 高级功能和架构文档。

**退出条件**：

- 新用户不需要先阅读架构文档。
- 中英文文档命令、版本和支持状态一致。
- 所有宣传数据有来源和日期。

### 阶段六：小范围真实用户测试

**状态**：首轮隔离环境模拟真实用户 CLI 验收已通过。真实外部用户尚未招募；MCP 客户端对话路径和外部用户留存仍待验证。

**目标**：验证用户是否能独立完成任务，并确认持续价值。

**测试任务**：

1. 在干净隔离环境安装并运行 `carrymem version`。
2. 执行 `carrymem init` 和 `carrymem doctor --json`。
3. 配置一个本地 MCP 客户端，重启后验证 `health_check` 和 `tools/list`。
4. 写入三条偏好。
5. 开启新会话并召回。
6. 使用第二个独立客户端进程共享同一个数据库并召回。
7. 查看来源、作用域、版本和 `storage_key`。
8. 修改、查看版本历史、删除一条记忆，并再次召回确认删除。
9. 执行导出或备份恢复，确认数据完整性。

**文档与命令验收记录**：

- 面向用户文档：英文安装指南、英文快速开始、中文安装指南和中文快速开始已完成命令审计。
- 实际执行：隔离 HOME 中通过 `version`、`init`、`doctor --json`、`add`、`list`、`pack`、`unpack` 和恢复后搜索；安装验证、CLI、MCP Server、MCP E2E 共 269 项测试通过。
- 修复：统一 `python3 -m carrymem version` 备用命令；`pack/unpack` 现在读取 `CARRYMEM_CONFIG_FILE` 指定的 YAML/JSON 配置。
- 已知环境信息：无网络时可出现可选向量模型下载警告；规则分类和 FTS5 主路径仍可运行。`doctor --json` 在隔离环境可能报告 CLI 不在 PATH，这属于环境检查结果，不是安装失败。

**本轮验收记录**：

- 参与者：本机模拟用户流程；不是外部用户样本。
- 客户端：本轮通过 CLI 和两个独立本地进程路径验证；TRAE/Workbuddy 真实同步证据已存在。
- 第三客户端：按用户决定跳过。
- 数据：临时 SQLite，不接触用户默认数据库。
- 结果：通过。`carrymem init` 后用户记忆数为 0；写入 3 条记忆；编辑后版本升为 2；备份文件生成；删除后再次搜索 PostgreSQL 返回 0 条。
- 修复：移除 `init` 写入“CarryMem initialized successfully!”的内部记忆，并使 `init`、`version` 使用动态配置和数据库路径。
- 自动化回归：CLI 增强与综合测试 122 passed；CLI、MCP 工作流和 MCP 工具 E2E 回归共 175 passed；真实 MCP stdio 生命周期通过 33 工具发现、健康检查、写入、更新、历史、召回和删除闭环。

**采集指标**：

- 安装成功率。
- 首次写入成功率。
- 首次召回成功率。
- 跨客户端召回成功率。
- 查看/修改/历史/删除闭环成功率。
- 导出恢复成功率。
- 7 日留存率：外部用户测试阶段采集，本轮不虚报。
- 错误记忆比例和推荐意愿：外部用户测试阶段采集，本轮不虚报。

**外部用户测试执行表**：

| 项目 | 要求 |
|---|---|
| 样本量 | 5–10 名真实用户；不把维护者或自动化脚本计入样本 |
| 用户类型 | 经常使用 TRAE、Workbuddy 或其他本地 MCP 客户端的开发者 |
| 测试环境 | 用户自己的客户端；使用独立数据库，不要求提供记忆内容 |
| 必做任务 | 安装、初始化、`health_check`、首次写入、新会话召回、查看 `storage_key`、更新、历史、删除 |
| 可选任务 | 第二个 MCP 客户端召回、备份或导出/导入 |
| 记录方式 | 通过 Beta Feedback 模板提交；记录版本、系统、客户端、安装方式、成功/失败和错误信息 |
| 隐私边界 | 不收集原始记忆内容；用户只需提供脱敏后的错误信息和结果 |
| 单用户完成标准 | 首次写入和新会话召回成功；失败时记录阻塞点 |
| 阶段完成标准 | 至少 5 名用户完成必做任务；阻塞性问题关闭或进入技术债；不以自动化测试代替真实用户记录 |

**给外部用户的最小测试指引**：

1. 安装并运行 `carrymem version`。
2. 运行 `carrymem init`、`carrymem setup-mcp --all --global` 和 `carrymem doctor`。
3. 重启客户端，调用 `health_check`。
4. 在对话框中写入一条非敏感偏好。
5. 开启新会话，要求客户端查询该偏好。
6. 查询并记录 `storage_key`、来源、作用域和版本，不提交原始内容。
7. 修改该记忆，查看历史，然后删除并再次查询确认删除。
8. 使用 [.github/ISSUE_TEMPLATE/beta_feedback.md](../.github/ISSUE_TEMPLATE/beta_feedback.md) 提交结果。

**退出条件**：

- 至少一轮隔离环境模拟真实用户记录完成：已完成。
- 至少一轮真实外部用户记录完成：未完成。
- 至少一轮真实 MCP 客户端对话记录完成：未完成。
- 找到并修复阻塞性安装、配置和召回问题：当前已完成首轮阻塞问题修复，仍需外部验证。
- 跨客户端召回成功率达到推广门槛：尚未测量。

**团队版候选能力**：

    ↓

## 6. 发布和推广门禁

在阶段六完成前，不进行大规模推广。

发布前必须同时满足：

- 核心 CI 通过。
- 依赖安全检查通过。
- 当前本地推广材料只宣传 TRAE 与 Workbuddy 的真实证据；第三客户端不作为本轮门禁。
- 安装、写入、召回、删除 E2E 通过；首轮隔离 CLI 和 MCP stdio 模拟验收已通过。
- 外部用户测试完成前，不声称真实用户留存、错误记忆率、推荐意愿或推广门槛已达成。
- 文档与实际命令一致。
- 发布版本在 PyPI 可查询。
- 不能只凭 tag 或 workflow 触发声称已发布。
