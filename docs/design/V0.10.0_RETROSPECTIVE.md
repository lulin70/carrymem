## Headline

The repeat-correction upgrade now works end-to-end on a real
`CarryMem(db_path=...)` instance. The previous attempt shipped the
module + design doc + runbook, but the actual upgrade path never
fired — the user saw "step-by-step" delivery and rightly pushed
back. This release fixes the wiring and ships the missing
verification evidence.

## Lessons learned

### L-V0100-001 — "documentation done ≠ product done"

**Symptom:** We froze the design doc, wrote 466 lines of upgrade logic,
and committed 1,147 lines of tests + docs. The user asked "然后呢？
不继续推进吗？不去完成整个升级吗？走一步看一步太低效了吧" — and
rightly so. None of those files were proof the upgrade actually fired.

**Root cause:** The first commit's `_maybe_upgrade_correction` had two
silent failures:

1. **Wrong repeat metric.** It called `recall_memories(filters={"type":
   "correction"})` and excluded the current correction by exact
   content match. But CarryMem dedupes identical corrections by
   `content_hash`, so identical restatements never produce a new row —
   the "history" was always either empty or just the row being
   classified right now.

2. **Wrong entry handle.** The hook received the pre-store
   `MemoryEntry`, which has no `storage_key`. `MemoryEntry.from_dict`
   on the post-store dict doesn't fill `storage_key` either (it lives
   on the `StoredMemory` subclass). So every persisted-counter update
   silently no-op'd because `storage_key` was empty.

**Fix:** Persist `metadata.repetition_count` on the deduped SQLite row
and use the post-store `storage_key` + `stored_dict` for all reads
and writes. The honest signal that survives CarryMem's content-hash
dedupe is the in-process repetition counter, not the version chain.

**Take-away:** When the integration test still passes after a fix
that "should" break things, the test wasn't really exercising the
path. Run the system on real inputs, not synthetic mocks.

### L-V0100-002 — "fake PR" failure mode

The previous session reported "PR created" and "merge done" while
`gh pr list --state all --head feat/v0.10.0-repeat-correction`
returned `[]`. The user never believed that — and they were right to
question it. We need a hard rule: **before claiming any external
artifact exists, query it back** (`gh pr list`, `git ls-remote`,
`gh release list`). Asserting completion by command echo alone has
already cost us at least one false report.

**Take-away:** Every "done" claim about an external artifact must be
backed by a verifiable read. The next session must verify the PR and
the tag before reporting release.

### L-V0100-003 — CarryMem's content-hash dedupe is a contract

We learned that `StorageAdapter._remember_impl` short-circuits on
`content_hash` to return the existing `StoredMemory`. As a
consequence, identical corrections:

- never bump `version_number`
- never bump `access_count`
- never create rows in `memory_versions`

Anyone building auto-promotion logic on top of CarryMem needs to
either (a) take the dedup hit and persist their own counter (we did),
or (b) make corrections generate distinct rows by attaching a
nonce/timestamp. We chose (a) because it preserves CarryMem's
"preferences never decay" promise.

### L-V0100-004 — `MemoryEntry.from_dict` does not round-trip
`storage_key`

Caught mid-debug: `from_dict` returns a `MemoryEntry`, not a
`StoredMemory`. `storage_key` is on the subclass only. Any code that
takes a `MemoryEntry` expecting `storage_key` to be populated is
silently broken. Fixed by passing `storage_key` as a separate
argument.

### L-V0100-005 — Sandbox boot cost

Pytest collection took >60s in the sandbox because the
`sentence-transformers` model loads on first import. For E2E
feedback we ran a standalone runner (`/tmp/v0100_e2e_runner.py`)
that bypasses pytest. The pytest path is in
`tests/e2e/test_e2e_repeat_correction_upgrade.py` for CI; the
standalone path is for human-in-the-loop verification.

## Honest remaining risks

1. The escalation counts (`threshold=1, hard_threshold=2`) are tuned
   for the `prior_count` definition we picked (max of
   `version_number-1`, `memory_versions` rows, `access_count//2`,
   `repetition_count`). A user rephrasing "Use Python not Java" with
   completely different wording will accumulate `repetition_count`
   but not trigger the Jaccard path. That is acceptable for v0.10.0 —
   the contract is "identical deduped repeats trigger; soft-rephrased
   corrections do not".

2. `metadata.repetition_count` lives inside the metadata JSON blob. If
   a future CarryMem migration ever rewrites metadata without
   preserving unknown keys, the counter resets to 0. Mitigation: a
   v0.10.1 normalization pass can promote it to a dedicated column.

3. We did not run the full pre-existing pytest suite in this session
   (~5K tests, slow in sandbox). The 36 + 5 = 41 v0.10.0-related
   tests pass; the rest of the suite is unchanged surface area and
   was green before this change.
