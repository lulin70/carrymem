### 3.2 benchmark.yml 幽灵参数（比审计结论更严重）

- `--benchmark-json` 依赖 `pytest-benchmark`，但 `tests/test_performance_benchmark.py` 是**手写计时**、根本不用该插件 → pytest 直接 usage error 退出。
- 更糟：`pytest ... | tee` 管道使退出码被 `tee` 吞掉 → **CI 基准 job 从未真正跑过基准**，一直假绿。
- 修复：删除幽灵参数；`set -o pipefail` + `PIPESTATUS[0]` 记录真实退出码（job 保持 advisory 语义，阈值违规仍走 ::warning::）；删除永不存在的 `benchmark_results/` 幽灵 artifact 步骤。

## 7. 教训（Lessons Learned）

- **L-V0101-001 工具层并发写同一文件会丢改动**：同文件两次 Edit 并行下发时，后一次基于旧快照覆盖前一次（server.json 丢工具块、smithery.yaml 丢版本行的直接原因）。规则：**同一文件的多次编辑必须串行**；关键编辑后必须 grep 复核实际落盘内容，不信任工具回显。
- **L-V0101-002 测试重写时类名冲突会静默吞测试**：新建类与既有类同名 → Python 后定义覆盖前定义 → 原测试从收集中消失且无任何告警。规则：重命名/新增测试类后必须对比收集数（collected N）变化。
- **L-V0101-003 断言前提必须显式验证**：新测试的消息选择（"Secret project details"）被分类为噪声、根本不入库，导致 backup/restore 测试失败——失败暴露了前提错误，也顺带暴露 `test_backup_creates_file` 的空库假通过。规则：E2E 测试以 `stored is True` 断言锁定前提。
- **L-V0101-004 CI 管道吞退出码**：`pytest | tee` 在无 pipefail 时永远返回 tee 的退出码，配合幽灵 `--benchmark-json` 参数 → 基准 job 长期假绿。规则：CI 中跑 pytest 的管道必须 `set -o pipefail`。
- **L-V0101-005 审计 finding 必须先复现再修**：本轮 2 条审计结论（__main__ 22s、冻结矛盾）复核不可复现，避免了一次无效"修复"。
