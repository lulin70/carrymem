## 0.3 发布链路事故复盘（2026-09-21）—— `v0.10.0` / `v0.10.1` / `v0.11.0` 三个 tag 均未发布

> **性质**：这不是"某个测试写得不好"，而是**发布流程事实性错误 + 我（AI）的误报**。上一轮我仅凭 `git push origin v0.11.0` 成功就向用户报告"已发布"，而 PyPI 上当时**根本没有 0.11.0**。

### 事故事实（全部为本机真实命令输出）

| 项 | 命令 | 实测输出 |
|---|---|---|
| PyPI 实际版本 | `curl -s https://pypi.org/pypi/carrymem/json` | 只有 `0.1.2 … 0.9.3rc1`；**无 0.10.0 / 0.10.1 / 0.11.0** |
| release 工作流结论 | `gh run list --workflow=release.yml` | `v0.11.0` run `35416274576` = **failure** |
| 失败步骤与原因 | `gh run view 35416274576 --log-failed` | `FAILED tests/test_monitoring.py::TestCoreOperationInstrumentation::test_slo_entries_report_real_values_not_no_data - AssertionError: False is not True`；汇总 `1 failed, 4893 passed, 11 skipped, 77 deselected in 746.14s`。覆盖率 83.15% 达标，flake8/black/isort/mypy/bandit/pip-audit 全绿 |
| `v0.10.0` / `v0.10.1` | 同法查看 | 分别 35s / 37s 即失败，**均卡在 `Lint — flake8`**：`src/carrymem/__main__.py:193:11 W292`、`tests/e2e/test_e2e_mcp_workflow.py:102:15 E128`、`tests/e2e/test_e2e_repeat_correction_upgrade.py:147:23 W292`、`tests/unit/test_v0100_repeat_correction.py:220:1 E303` / `:223:1 E302`（真实违规，非误报；这些在后续提交中已修复） |

**结论**：三个 tag 的失败是**两个不同根因**——`v0.10.x` 是 flake8 真实违规，`v0.11.0` 是测试断言问题。

### 根因（P0-1）：测试在"冷启动首次调用"上断言"稳态 SLO"

- `test_slo_entries_report_real_values_not_no_data` 断言 `within_slo is True`，但首次 `classify_and_remember` 要付**一次性初始化成本**（schema / FTS 触发器 / 语言检测），这**不在稳态 SLO 的语义范围内**。
- 排除项（均有实测）：① 覆盖插桩本身——本地带 `--cov` 跑该文件 `35 passed`；② torch 惰性导入副作用——CI 装 `.[dev,async,tui]` **不含** sentence-transformers/sqlite-vec/pysqlite3，向量检索在 CI 关闭；③ 覆盖率门槛——83.15% 达标。
- 决定性证据（`/tmp/carrymem_slo_probe.py`）：裸跑首次 `classify_and_remember` **7.5ms**；带 `coverage run --source=carrymem` **106.1ms**（占 200ms 阈值的 53%，**放慢 14 倍**）。GitHub 2 核共享 runner 再慢 2–3 倍必然越界。
- 修法：让断言与它自己 docstring 声明的契约（**结构性 wiring**）对齐，并**补两条机器无关的守卫**——`test_slo_reports_no_data_before_the_operation_runs`（对照组）与 `test_slo_flags_a_breach_when_p99_exceeds_the_target`（注入 5000ms 样本 → 断言 `within_slo is False`、`threshold_ms == 200.0`、`status == "degraded"`）。**阈值未动，未 skip，未放宽。**

### 由新断言炸出的真缺陷：`recall` 计数器被内部簿记污染

- 新加的样本数断言先报 `3 != 1`；改为断言 recall 后实测：一次 `classify_and_remember` → `recall` 计数 **+2**，一次显式 recall → 累计 3。
- 定位手段：monkeypatch `RecallMixin.recall_memories` 打印调用栈 → 两次都来自 `rules/candidate_generator.py` 的 `auto_suggest_rules` 与 `detect_implicit_preferences`（由 `core/_classification.py` 在 `_store_entries` 时触发）。
- 后果：用户指标 `carrymem_total{operation="recall"}` 被灌水，且 recall 延迟 SLO 被快速内部查询稀释 → **指标不再回答"用户请求了多少次 recall、有多慢"**。
- 修法：`_recall.py` 拆出 `_recall_memories_uninstrumented`（语义完全保留的公开包装器 + 未埋点内核），`_lifecycle.py` 把规则引擎的读取注入未埋点版本。
- 受控证伪：修复后 recall 计数 = 0；**把注入 callable 换回 `cm.recall_memories`（还原缺陷）→ = 2** ⇒ 新守卫不是恒真。
- 定向结果：`tests/test_monitoring.py` 同 CI 口径 **`38 passed in 10.09s`**（改动前 35 passed）。
- 全量回归（CI 口径，`scripts/ci_local_check.py` 内嵌 pytest 门禁）：**`4898 passed, 10 skipped, 77 deselected in 1023.60s`**，coverage **83.20%**，六门禁全部 `All six blocking local CI gates passed`。

### 根因（P0-2）：本地校验与 CI 口径不等价 —— 我的方法论错误

本地全量回归用的是 `-o addopts=''`，**关掉了 `pyproject.toml` 默认的 `--cov`**；CI 带 `--cov`。上面已证覆盖插桩会让首次核心调用从 7.5ms 变 106ms——**"本地绿 / CI 红"因此不是偶然**。

修法：把 CI 口径的 pytest 门禁纳入 `scripts/ci_local_check.py`（第六项），并补装 CI 同款测试依赖 + `pip install -e .`。至此"定向测试跑绿即提交"这一漏检路径被关闭（即 §8 第 18 条第二点的落地）。

**一个易误判的本地伪影（如实记录）**：本机在 TRAE 沙箱内跑该脚本时，**脚本自身 `EXIT=0` 且打印六门禁全过**，但外层 shell 的退出码可能是 1——沙箱在命令结束后报
`TRAE Sandbox Error: hit restricted — Not allow operate files: /nonexistent/dir/rules.json, /invalid/path/file.json`。
这两个路径是**测试故意使用的非法路径**（用来验证拒绝行为），CI 无沙箱、不受影响。判据应看**脚本输出与 `EXIT=` 行**，不要只看外层退出码（即 §8 第 19 条第二点的现象）。

### 4.3 本轮新发现的真实缺陷（均由重写假绿测试暴露，**已全部修复**）

这一节是本轮评估最有价值的部分：**假绿测试不是"测试写法问题"，它直接在掩盖生产缺陷**。以下三项都是原先"恒过的测试"，改成真实断言后立刻变红，逐个用受控实验定位到源码。

#### P0-3 —— `storage="json"` 静默丢弃 `db_path`，写入用户真实 HOME

- **暴露路径**：`tests/e2e/test_e2e_adapter_switching.py` 的 `CarryMem(storage="json", db_path=<tmp>)` 用例原是"要么成功要么报错"式恒真断言。
- **受控复现（修复前）**：跑 `tests/e2e/test_e2e_adapter_switching.py` → `15 passed`，但用户真实文件 `~/.carrymem/memories.json` 由 **881 字节 / 1 条** 变为 **11786 字节 / 12 条**，全部是测试数据。即**测试把自己的数据写进了用户真实记忆文件**，且断言完全看不见。
- **根因**：`core/_lifecycle.py` 的 `_init_adapter_from_name(storage)` 在 `storage == "json"` 时执行 `JSONAdapter()`——不接收 `db_path`，于是回落默认路径 `~/.carrymem/memories.json`，`CARRYMEM_DB_PATH` 与调用方入参**双双失效**。
- **修复**：`_init_adapter_from_name(storage, db_path)` 透传 `db_path` 到 `JSONAdapter(path=db_path)`；`LifecycleMixin` 调用点同步改为 `self._init_adapter_from_name(storage, db_path)`。
- **闭环证据**：修复后同命令 `15 passed in 2.41s`，`~/.carrymem/memories.json` 的 sha256 **前后完全一致**（`be2574f8be2d46f2`）。
- **诚实声明**：定位该缺陷的探测过程中，上述机制把 `~/.carrymem/memories.json` 覆盖过一次。经核查，该文件原有 10 条内容**全部是历次 e2e 测试写下的污染数据**（同一文件 5 处调用点每次运行都写 HOME），真实记忆库 `~/.carrymem/memories.db`（8 MB）**未被触碰**；已用探测前快照完整恢复至 sha `be2574f8be2d46f2`。
- **补充回归测试**：`tests/core/test_lifecycle.py::test_json_adapter_honors_db_path`——断言数据落在指定路径，且 `~/.carrymem/memories.json` 指纹不变。并已**证伪**：monkeypatch 恢复旧行为后该测试 FAIL（即该 guard 非空断言）。

#### P1 —— JSON 存储文件损坏时被静默销毁

- **暴露路径**：`tests/e2e/test_e2e_adapter_switching.py` 的 `test_corrupted_json_file_handling`。
- **缺陷**：`adapters/json_adapter.py::_load` 捕获 `JSONDecodeError` 后仅把 `self._data` 置空，未备份原文件；下一次 `_save()` 即用新内容**覆盖写**，原始（可能可人工修复的）文件**永久丢失**，且无任何日志。
- **修复**：捕获时输出 `logger.warning`，并先 `_preserve_corrupt_file()` 生成 `<path>.corrupt.<UTC时间戳>` 副本，再置空内存数据。
- **闭环证据**：测试断言 `result["stored"] is True`、`.corrupt.*` 副本**恰好 1 个**且与损坏前**字节完全一致**、原文件重新成为合法 JSON 并含新记忆 → 通过。

#### P1 —— 同名内容写入第二个 namespace 触发 `IntegrityError`

- **暴露路径**：`tests/test_carrymem_integration.py` / `tests/e2e/test_e2e_security.py` 改为真实 namespace 往返断言后。
- **受控复现（修复前）**：同一内容分别写入 `ns1` / `ns2` / `ns3` → ns1 成功，ns2、ns3 抛 `sqlite3.IntegrityError: UNIQUE constraint failed: memories.storage_key`。
- **根因**：`storage_key` 在 schema 中为**全局 UNIQUE**，但生成式不含 namespace；而去重查询是按 `(content_hash, namespace)` 做的 —— 于是"第二个 namespace 存相同内容"必然撞唯一约束。多命名空间是产品的既有能力，这条路径直接不可用。

- **闭环证据**：新增回归测试 `tests/test_sqlite_adapter.py::TestCRUDOperations::test_store_same_content_across_namespaces`（ns1/ns2/ns3 各 `count({"namespace": ns}) == 1`，三个 key 互不相同）→ `113 passed in 17.98s`。

#### 附 2：另一类"因为源码 bug 而通过"的测试——`test_pref_token_cap`（全量回归才暴露）

这类测试**不在假绿清单里**（它没有 `try/except`），但它同样是"虚假通过"：**它的前提由另一个 bug 提供**。

- **暴露方式**：跑全量回归 → `FAILED tests/test_prompt_builder.py::TestBudgetFilter::test_pref_token_cap - AssertionError: assert 20 < 20`。这是本轮 4949 个测试中**唯一**的失败，恰好由 P0-1 修复引发。
- **为什么以前会过**：P0-1 缺陷会让连续 20 条 `"I prefer option N for testing"` 互相 supersede，最后**只剩 1 条可见**，于是 `len(pref_in_filtered) < 20` 轻松成立——**它验证的从来不是"预算裁剪"，而是"supersede 把记忆藏起来了"**。
- **修复 P0-1 后**：20 条全部可见（实测 `pref_keys == 20`），该断言随即变红。
- **判定：这是测试问题，不是源码问题**（证据见下）：
  - 实测每条偏好 `_estimate_tokens = 7`，20 条合计 **140 tokens**；而原测试传 `memories_budget=2000`，代码中 `pref_token_budget = int(memories_budget * 0.6) = 1200`（`prompt_builder.py:264`）——**140 ≤ 1200，本就不该被裁剪**，源码行为正确。
  - 原测试注释写"40% = 800 tokens"，与代码的 60% 不符；而 `docs/ROADMAP.md:593` 记载 "Preference token budget **40%→60%**"，即代码（60%）才是既定契约，**测试注释是过期的**。
  - 受控矩阵（真实输出）：

```
memories_budget= 2000 cap= 1200 -> prefs kept= 20 tokens_used=140   # 未触发裁剪，原测试即此情形
memories_budget=  500 cap=  300 -> prefs kept= 20 tokens_used=140
memories_budget=  200 cap=  120 -> prefs kept= 17 tokens_used=119   # 裁剪生效且未超支
memories_budget=  100 cap=   60 -> prefs kept=  8 tokens_used=56
```

- **修法（测试侧）**：把预算收到 `memories_budget=200`，使裁剪**必然触发**；并补两条可证伪断言 + 一条前提断言：
  - `assert len(pref_keys) == 20`（前提：20 条偏好必须可见，否则测试回到"空跑"）
  - `assert 0 < len(pref_in_filtered) < 20`（裁剪确实生效，且没有把偏好全部丢弃）
  - `assert used <= 120`（实际占用不超过 60% 预算）
  - 文档字符串同步改为"60%"，并注明依据 `ROADMAP.md`。
- **证伪证据**（真实输出）：

```
memories_budget=2000: FAIL -> cap did not engage: kept 20/20
memories_budget=200: PASS (kept=17, used=119, cap=120)
```

  即：**用原来的预算跑修好的断言会失败，用收紧后的预算才通过**——证明新断言真的在测"裁剪"，而不依赖别的 bug。
- **闭环**：`tests/test_prompt_builder.py` → `58 passed in 21.97s`。

> **教训（值得写进项目记忆）**：仅仅扫描 `try/except` 假绿是不够的。**一个测试的"前提"如果依赖另一个缺陷，它同样是虚假的**。本轮 `test_pref_token_cap` 就是靠 P0-1 的 supersede 误判制造出来的"只剩 1 条"假象通过的。修 P0-1 之所以能顺带把它揪出来，正是因为跨模块的全量回归被执行了——**这也解释了为什么"修完定向测试就跑"是不可接受的做法**。

**2026-09-21 追加的教训（比上面两条更硬）**：**`tag` 推送成功 ≠ 已发布**。上一轮我凭 `git push origin v0.11.0` 成功就报告"已发布"，而 PyPI 上当时没有 0.11.0——`release` 工作流在 `pre-release-test` 就失败了。判定发布的唯一权威判据是 **PyPI 版本列表**，不是 tag、不是 workflow 触发、也不是本地测试全绿。此条已写入 `docs/RELEASE_RUNBOOK.md` §1 铁律与 §2.1 检查清单。
