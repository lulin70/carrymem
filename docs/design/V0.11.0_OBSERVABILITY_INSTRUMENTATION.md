# CarryMem v0.11.0 可观测性真埋点设计

> **日期**: 2026-09-18
> **状态**: 设计已定稿，实现与验证中（活文档，逐项更新）
> **决策来源**: [V0.11.0_PROJECT_REVIEW.md](V0.11.0_PROJECT_REVIEW.md) §9 —— 产品决策 **选 A（真埋点）**，不删能力、不降级为"实验性"
> **关联报告项**: §2.7 可观测性 D（62）、§8 P1 第 6 条

## 1. 问题回顾（为什么必须做这件事）

v0.11.0 评审实测结论：

- `monitoring/__init__.py` 的 `record_latency` / `set_gauge` / `increment` 在**全 `src/` 内零调用点**；
- 唯一实例化点 `integration/layer2_mcp/http_server.py:85` 创建一个**孤立的** `MetricsCollector()`，没有任何代码往里写数据；
- 后果：`GET /metrics` 实际只输出 `carrymem_uptime_seconds`；`HealthChecker` 的 3 条 SLO 恒为 `status: "no_data"`，**永远不会 degraded**（即"永远健康"的假监控）。

本项目既有教训 **L-V460-006**：「运维文档不得声明未接线的 Prometheus 指标——写告警前先回答"这个 series 由谁在哪个进程里产生"」。本设计文档的核心就是**逐条回答这句话**。

---

## 2. 判定标准（本设计的第一原则）

> **任何一个对外可见的 series，必须能指出「哪个进程、哪条代码路径、什么条件下」写出样本。指不出来的，不允许出现在 `/metrics` 里。**

三条推论：

1. **不允许"定义了但没人写"的 series**（当前 `set_gauge` 的处境）。
2. **不允许"写入了但读不到"的 series**（写入方与 `/metrics` 读取方必须是同一个 collector 实例——这是当前最大的结构性问题）。
3. **不允许"看起来健康其实没数据"**：`no_data` 必须只出现在"该操作真的没发生过"的场景，而不是"埋点没写"。

## 3. 指标清单（**唯一权威表**：每个 series 的产生者）

| Series | 类型 | 标签 | 产生者（进程 / 代码路径） | 触发条件 | 进 SLO？ |
|---|---|---|---|---|---|
| `carrymem_total{operation="classify_and_remember"}` | counter | `operation` | **任意 Python 进程** / `core/_memory_crud.py::MemoryCRUDMixin.classify_and_remember` | 该调用**成功返回**时 +1 | 否 |
| `carrymem_total{operation="recall"}` | counter | `operation` | 任意 Python 进程 / `core/_recall.py::RecallMixin.recall_memories` | 该调用**成功返回**时 +1 | 否 |
| `carrymem_total{operation="classify_and_remember_errors"}` | counter | `operation` | 同上（`classify_and_remember`） | 该调用**抛异常**时 +1（`finally` 之外，异常路径） | 否 |
| `carrymem_total{operation="recall_errors"}` | counter | `operation` | 同上（`recall_memories`） | 该调用**抛异常**时 +1 | 否 |
| `carrymem_latency_ms{operation="classify_and_remember",quantile=...}` + `_sum`/`_count` | summary | `operation`,`quantile` | 任意 Python 进程 / `classify_and_remember` | 每次调用结束（成功与失败**都**记样本） | ✅ P99 < 200ms |
| `carrymem_latency_ms{operation="recall",...}` + `_sum`/`_count` | summary | `operation`,`quantile` | 任意 Python 进程 / `recall_memories` | 每次调用结束 | ✅ P99 < 500ms |
| `carrymem_latency_ms{operation="startup",...}` + `_sum`/`_count` | summary | `operation`,`quantile` | 任意 Python 进程 / `core/_lifecycle.py::LifecycleMixin.__init__` 末尾 | **每个进程只记一次**（该进程内首次构造 `CarryMem` 时） | ✅ < 2000ms |
| `carrymem_sse_clients` | gauge | 无 | `integration/layer2_mcp/http_server.py`（HTTP 服务进程） | SSE 客户端接入 / 断开时 `set_gauge` 为当前活跃连接数 | 否 |
| `carrymem_uptime_seconds` | gauge | 无 | `monitoring/__init__.py::MetricsCollector` | 每次 `/metrics` 抓取时计算（已有行为，不变） | 否 |

**失败计数器为什么必须存在**：若只统计成功调用，一个"每次都失败"的操作会表现为 `no_data` → `HealthChecker` 判为"无数据即健康" → 故障被监控掩盖。这是 fail-open 的监控，必须避免。

**失败样本为什么也进 latency**：用户等待的时间包含失败路径（例如 30s 超时），把它排除会让 P99 系统性偏低。

**语义边界：`recall` 只统计"用户发起的 recall"**（2026-09-21 修订，实测发现并修复）

**存记忆过程中**共有 **3 条**内部读取路径会读已有记忆，全部属于**系统簿记**，不是用户请求的 recall：

| # | 触发点 | 位置 | 触发条件 |
|---|---|---|---|
| 1 | 规则候选生成（`auto_suggest_rules` / `detect_implicit_preferences`） | `rules/candidate_generator.py`，由 `core/_classification.py` 在 `_store_entries` 时触发 | 每次存记忆（**+2**） |
| 2 | 指代消解（coreference） | `core/_classification.py` 的 `_validate_and_resolve` | 消息含代词（`my` / `it` / `this` …）时（**+1**） |
| 3 | 纠错历史与纠错关键词匹配 | `core/_classification.py` 的纠错路径 | 消息被判为 correction 时（**+1 起**） |

- 修复前实测：一次 `classify_and_remember` 会让 `carrymem_total{operation="recall"}` **+2**（无代词消息）或 **+3**（含代词消息）；`recall` 与 `classify_and_remember` 的比值因此失真，同时把快速的内部查询混入 `carrymem_latency_ms{operation="recall"}`，**稀释**用户真实 recall 的 P99。
- 因此 `recall_memories` 拆为两层：**公开的埋点包装器**（用户路径）与 **`_recall_memories_uninstrumented`**（内部路径）。路径 1 由 `core/_lifecycle.py` 注入未埋点版本，路径 2/3 在 `core/_classification.py` 内直接调用未埋点版本。
- 守卫：`tests/test_monitoring.py::test_storing_a_memory_does_not_count_as_a_recall` 断言"存一条记忆后 `recall` 不在 counters 也不在 latency 中"。
  **一次真实的守卫失效教训（0.11.1 → 0.11.2）**：该守卫最初只用**无代词**消息，路径 2 因此从未被执行——修复"看起来通过了"，实际只关掉了 3 条路径中的 1 条。0.11.2 改为用 `subTest` 覆盖 4 种消息形态（含 2 条带代词、1 条 correction），并加对照组 `test_an_explicit_recall_still_counts`（证明守卫不是靠"永不计入"通过）。受控证伪：还原路径 2 的埋点调用 → **恰好两条带代词用例 FAIL**，而旧版（无代词）守卫对同一份坏源码仍然通过。
- 判定原则（可推广）：
  1. **指标标签的语义由"谁发起"决定，不由"走了哪条代码路径"决定**。同一底层函数被不同主体调用时，必须区分埋点与未埋点入口。
  2. **守卫必须覆盖被修复分支的触发条件**。只覆盖"默认路径"的守卫会给出假绿——本次代词就是触发条件。

## 5. `/metrics` 对外契约（本次起成为需维护的契约）

- **endpoint**：`GET /metrics`，`Content-Type: text/plain; version=0.0.4; charset=utf-8`，**免鉴权**（与 `/health`、`/healthz` 一致，见 `http_server.py:221-240`）。
- **稳定 series 名**：上表第一列。改名前必须视为破坏性变更（写进 CHANGELOG）。
- **单位**：`carrymem_latency_ms` 系列一律**毫秒**；`carrymem_uptime_seconds` 为秒；`carrymem_sse_clients` 为个数。
- **语义边界（诚实声明，必须与 README 一致）**：
  1. **进程内语义**：所有 counter/latency 都是**当前进程**的累计值，进程重启即归零。CarryMem 是本地单实例工具（`localhost:8000`），**不做多实例聚合**。
  2. **`startup` 的定义**：`import carrymem` 开始 → 该进程内**首次** `CarryMem()` 构造完成。它**包含**模块加载与首次构造，但**不再包含** `sentence_transformers` → torch 的加载——后者自 P1#10（§10）起为惰性导入，仅在真正启用向量检索时才发生。它**不包含** Python 解释器启动与 CLI 参数解析。
  3. **`no_data` 的含义**：仅表示"该操作在本进程内尚未发生"。若某操作持续发生却始终 `no_data`，那才是埋点故障。
  4. **单进程内多次构造 `CarryMem`**：只有第一次计入 `startup`；后续构造不再产生样本（否则"距 import 的时间"会随进程存活时长单调增长，得到无意义的巨大值）。
  5. **`carrymem_uptime_seconds` 的口径未变**：它是 **collector 自身的存活时长**（在首次被创建时开始计时），不是 OS 进程启动时刻。因为 collector 在首次 `CarryMem()` 构造（`record_startup_once`）或首个 `MCPHTTPServer` 构造时创建，该值会比真实进程 uptime 少约一个 `startup` 时长。明确记录以免被误读为进程 uptime。

## 6. 实现设计

### 6.1 结构性问题：写入方与读取方必须是同一个 collector

现状：`http_server.py:85` `self._metrics = MetricsCollector()` —— 这是唯一实例，且只有 `/metrics` 读它。

方案：在 `monitoring/__init__.py` 提供**进程级单例**

```python
_GLOBAL_COLLECTOR: Optional[MetricsCollector] = None

def get_metrics_collector() -> MetricsCollector:
    """Return the process-wide MetricsCollector (created on first use)."""
```

- `core/` 埋点写 `get_metrics_collector()`；
- `MCPHTTPServer.__init__` 改为 `self._metrics = get_metrics_collector()`，`HealthChecker` 也用同一个实例。

选单例而不是"从 CarryMem 构造参数一路透传"的理由：`CarryMem` 由 mixin 组合（`_lifecycle` / `_memory_crud` / `_recall`），透传需要改构造签名、facade、`Handlers`、`AsyncCarryMem` 与所有测试构造点；而"可观测性"本就是**进程级**关注点，单例是它的自然模型。代价（写在 §5 边界里）是"每进程一份、重启归零"。

### 6.2 埋点位置（具体到行）

| 文件 | 位置 | 改动 |
|---|---|---|
| `monitoring/__init__.py` | 文件末尾区 | 新增 `get_metrics_collector()`、`mark_startup_reference()`、`record_startup_once()`；gauge 导出改为**每个 gauge 一条 `# TYPE`**（当前统一写 `# TYPE carrymem_gauge gauge` 却不发同名样本，契约不干净） |
| `carrymem/__init__.py` | 顶部（在重 import 之前） | 调用 `mark_startup_reference()` 记录 T0 |
| `core/_lifecycle.py` | `__init__` 返回前 | `record_startup_once()` |
| `core/_memory_crud.py` | `classify_and_remember` | `try/except/finally`：成功 → `increment`；异常 → `increment(..._errors)`；`finally` → `record_latency` |
| `core/_recall.py` | `recall_memories` | 同上（`recall` / `recall_errors`）。**2026-09-21 修订**：拆出未埋点内核 `_recall_memories_uninstrumented`，供内部簿记读取使用（见 §3「语义边界」） |
| `integration/layer2_mcp/http_server.py` | `__init__`、`_handle_sse` | 用单例 collector；SSE 接入/断开时 `set_gauge("carrymem_sse_clients", len(self._clients))` |

埋点实现约束：
- **埋点不得改变被观测行为**：埋点代码自身抛异常会污染业务路径。因此 `record_latency` / `increment` 调用点保持"无副作用调用"，且不吞业务异常（业务异常必须原样抛出）。
- **不加装饰器**：装饰器需要额外处理 `functools.wraps` 与 mypy 泛型，且会让"这个操作在哪里被埋点"从源码上不可见（grep 不到调用点）。
- **实现形状按函数规模二分**（实测采用）：
  | 函数 | 规模 | 形状 |
  |---|---|---|
  | `classify_and_remember` | ~120 行、4 个 return 分支 + 2 处 raise | **公开包装器 + `_classify_and_remember_impl`**：原实现整体改名为 `_impl`（仅换 `def` 行），包装器持有 `try/except/finally`。避免为包 `try` 而把上百行整体重排缩进（大 diff、易错）。 |
  | `recall_memories` | ~15 行 | **内联 `try/except/finally`** + 抽出未埋点内核 `_recall_memories_uninstrumented`（2026-09-21 补，理由见 §3「语义边界」，与"拆 `_impl` 避免过度设计"不冲突：这里拆分的动机是**语义隔离**而非缩短函数）。 |
  - 代价：`classify_and_remember` 的调用栈多一层；异常类型与消息原样透传（有测试断言）。收益：埋点覆盖面是"整函数"而非"某几个分支"，早期 return（脱敏拦截、分类失败）也计入。

## 7. 校验方法（可证伪，禁止假绿）

| 层级 | 校验内容 | 为什么它不是假绿 |
|---|---|---|
| 单元 | `get_metrics_collector()` 多次调用返回同一对象；不同进程语义由 `reset()` 隔离 | 若返回新实例，断言立即失败 |
| 单元（核心埋点） | 真实 `CarryMem(storage="sqlite", db_path=":memory:")` → `reset()` 后断言 counters/latency **为空** → 调用 `classify_and_remember` → 断言计数 1、latency count ≥ 1 | 含**对照组**："调用前为空"排除了"断言恒真" |
| 单元（失败路径） | 调 `classify_and_remember("")` 触发 `ValidationError` → 断言 `classify_and_remember_errors == 1` 且成功计数为 0 | 若失败不埋点，断言失败 |
| 单元（startup 一次性） | `monkeypatch` 置 `_startup_reference`/`_startup_recorded` → 首次记录产生样本；再次调用**不新增样本** | 一次性语义若失效，第二次调用会多加样本 → 断言失败 |
| 集成（真实 HTTP e2e） | 起真实 `MCPHTTPServer`（真实 TCP + 真实 SQLite，tmp 目录）→ ① 抓 `/metrics` 断言**不含** `operation="classify_and_remember"`（对照组）→ ② POST 真实 `tools/call` 调 `classify_and_remember` → ③ 再抓 `/metrics` 断言出现 `carrymem_total{operation="classify_and_remember"} 1` 与 `carrymem_latency_ms_count{...} 1` → ④ 抓 `/healthz` 断言该 SLO 条目**不再是 `no_data`** 且 `within_slo` 存在 | ①③是同一端点的前后对照；若埋点没接上，③的 series 不会出现 → 失败。若 SLO 没读同一 collector，④的 `no_data` → 失败 |
| 全量回归 | `tests/` 全量（~13 分钟） | 独立埋点类 bug（如循环 import、埋点抛错）只会在全量里暴露 |
| 门禁 | `scripts/ci_local_check.py` 五门禁（用 CI 钉住的 black 版本） | 与 CI 一致 |

**额外控制实验（防"埋点自身成为故障源"）**：在失败路径断言"业务异常类型与消息未被埋点改变"（`pytest.raises(ValidationError)` 校验异常本身仍按原语义抛出）。

## 8. 诚实边界与遗留

1. `startup` 的样本每个进程只有 1 条，因此 `/metrics` 里 `carrymem_latency_ms_count{operation="startup"}` 恒为 1；p99/p95 语义退化（p95 在 `n<=20` 时为 `None`）。这是**有意设计**（startup 是进程级一次性事件），不是缺陷；文档已声明。
2. `carrymem_sse_clients` 只在 HTTP 服务进程有意义；stdio 模式下该 series 不出现。
3. 本次**不**接入 Prometheus 抓取配置、不写告警规则——本设计只保证"指标有真实产出"。告警规则属后续（若需要）另立设计，且必须以本表的产生者为前提。
4. **本仓不存在 `ALERT_RULES` 文档**（已全仓 grep 确认：`ALERT_RULES` 零命中，该名称属 DevSquad 仓）。故本次无告警文档需要同步。

### 9.6 教训

1. **"有指标定义"≠"有监控"**：只有当**写入方与读取方是同一个 collector 实例**时，`/metrics` 才是监控；本次最大的一处结构性缺陷正是"孤立实例"。判定方法可以固化为一句检查：*每个 series 的写入点与读取点是不是同一对象？*
2. **fail-open 监控比没有监控更危险**：只统计成功调用，会让"每次都失败"呈现为 `no_data`（健康）。故失败计数器与失败 sample 是本设计的**必需项**，不是锦上添花。
3. **埋点是导出契约的验收手段**：没有真实数据时，`None` 行、`quantile="0.5"` 实为均值这两个缺陷无法被发现——"先埋点，才可能验证导出正确"。
4. **诚实红灯优先于好看的数字**：`startup` 违约 8.8 倍时，修阈值或删检查都能"变绿"，但那正是本项目一直在反对的虚假自评。保留红灯 + 写入文档 + 立 P1 修复项。
5. **排障必须先确认"报错路径是否真实存在"**：本次一次真实排障被陈旧 `.pyc` 内嵌的幽灵路径带偏，直到对比 `ls` 才纠正。凡 traceback 指向的路径，先 `ls` 验证。

**实施中修正的一处设计偏差**：本表原写"冷启动冒烟沿用 `test_performance_smoke.py` 的 `CI_FACTOR` 宽松口径"。实测该口径在本机**是假绿**：本环境 `CI=true` ⇒ `CI_FACTOR=10`，预算 50s，而即使还原 eager import 也只花 20.37s，**守卫不会变红**。故改为**相对预算**——同一子进程内先测一组标准库 import 作对照，预算 = `max(3.0s, 12 × 对照)`：

- 两侧随机器速度同比缩放，避免"为 CI 放宽到失效"；
- 本地固定态：carrymem 0.57~0.61s / 对照 0.14~0.15s ⇒ 预算 3.00s（**5 倍余量**）；
- 本地 eager 态：20.37s ⇒ **变红**（已验证）；
- 12 倍系数的来源：固定态实测比值 ≈ 4 倍（0.6/0.15），取 3 倍余量。

**为什么不用"绝对秒数"**：固定预算要么在 CI 上过紧导致假红，要么宽到抓不住 17s 级回归——两者不可兼得（已实证）。相对口径是唯一同时满足"不假绿、不假红"的形式。

### 10.7 本次教训

1. **"放宽以适配 CI"会把守卫放空**：`CI_FACTOR` 类口径在 CI 上把预算放大 10 倍，恰好也把待检测的回归放大 10 倍——两者相消，守卫失效。**计时类守卫必须相对化**（同机对照），否则宁可不写。
2. **`import` 的"可用性探测"本身就是成本**：`try: from X import Y` 只延迟了异常处理，没有延迟执行。要延迟就必须让**探测**与**使用**都发生在调用点。
3. **惰性化的完整条件是"没有 eager 的复出口"**：`sqlite_adapter.py` 这个兼容 shim 若不改，它仍会在导入期把常量拉起来——第 1、2 步就白做了。改惰性时**必须顺着 re-export 链检查到底**。
4. **保留公开名字 ≠ 保留模块级赋值**：PEP 562 的模块 `__getattr__` 可以在不付代价的前提下维持 `from ... import NAME` 的可用性；配套用 `if TYPE_CHECKING` 让静态工具与 IDE 也看得见，比 `# noqa` 更诚实。
