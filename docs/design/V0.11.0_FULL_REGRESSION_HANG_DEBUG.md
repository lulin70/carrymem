# Debug full regression hang

Status: [RESOLVED — 2026-09-09]

## Symptom

The CarryMem full regression command remains alive after reaching approximately 59% and produces no additional log output. The pytest process reports zero CPU usage and has a multiprocessing resource tracker child.

Command under investigation:

```bash
PYTHONPATH=src /Users/lin/trae_projects/.venv/bin/python -m pytest tests/ --tb=short -q -o addopts='' -p no:cacheprovider
```

## Falsifiable hypotheses

1. A test is waiting on a SQLite lock or uncommitted transaction.
2. A test-created subprocess or multiprocessing resource is preventing progress.
3. A test is blocked in an unbounded wait or slow external operation.
4. The sandbox has stopped or suspended pytest rather than the test code deadlocking.
5. Pytest output buffering hides progress while tests continue.

## Evidence plan

- Inspect process state, child processes, open database files, and log mtime.
- Reproduce the suspected test boundary using collection order and bounded commands.
- Compare direct isolated execution with the full-suite process.
- Do not modify business logic before the cause is evidenced.

## Findings

- The log reached 59% and then stopped.
- The pytest process remains present with state `N` and zero CPU.
- A multiprocessing resource tracker child remains present.
- Several SQLite WAL files are open.
- A complete non-timeout regression run completed with `4939 passed, 13 skipped, 244 warnings, 25 subtests passed`.
- A later run with the pytest timeout plugin reached 100%; its only failure was the 30-second `python -m carrymem` subprocess budget. Direct execution was functionally correct, and the isolated test passed after increasing the test helper budget to 60 seconds.
- Detached `nohup` execution avoids the sandbox's stopped foreground process state and is the reliable method for long-running regression evidence.

## Conclusion

The repository deadlock hypotheses were not confirmed. The apparent hang was caused by sandbox process suspension/obscured progress, while the independent CLI failure was startup-time sensitivity. The debug record is closed without changing CarryMem business logic.
