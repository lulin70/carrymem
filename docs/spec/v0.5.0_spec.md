# CarryMem v0.5.0 Specification — 记忆从存储到关系图谱与压缩效率

> **版本**: v0.5.0 (Spec Draft)
> **创建日期**: 2026-07-01
> **状态**: Draft — 待 DevSquad 多角色 review
> **依据**: [竞品借鉴分析](../COMPETITIVE_ANALYSIS_MEMORY_GRAPH.md) + CarryMem 当前架构探索
> **范围**: 三个增强建议的详细设计，覆盖实体规范化、访问频率加权调优、摘要层+渐进式披露

---

## 1. 概述

### 1.1 目标

基于 cognee（三存储 ECL 管道 + Memify + Ontology）和 codebase-memory-mcp（Tree-Sitter + SQLite 图谱 + 120x token 节省）的借鉴分析，为 CarryMem v0.5.0 设计三个增强：

| # | 建议 | 类型 | 核心价值 |
|---|------|------|----------|
| 1 | 实体规范化（Ontology-lite） | **新功能** | 解决 "汽车制造商" vs "车辆生产商" 碎片化，提升 recall 准确率 |
| 2 | 访问频率加权增强 | **参数调优**（已存在） | 调优现有 `access_factor` 权重，让频繁访问记忆更显著 |
| 3 | 摘要层 + 渐进式披露 | **新功能** | token 节省，LLM 开关缺省关闭，TRAE 本地自动打开 |

### 1.2 设计原则

- **零 LLM 优先**：核心功能不依赖 LLM，LLM 仅作为可选增强（建议 3）
- **向后兼容**：所有变更通过 migration + 默认值保证不破坏现有 API
- **Simplicity First**：增量式增强，不重构现有架构
- **Surgical Changes**：每个建议独立可交付，互不依赖

### 1.3 关键架构发现（影响 spec 内容）

**重要**：架构探索发现"访问频率加权"已存在：

- `scoring.py:101-103` 已有 `access_factor(access_count) = 1.0 + log(1+max(0,n))*0.1`
- `schema.py:36,39` 已有 `access_count`/`last_accessed_at` 字段
- `recall_engine.py:262-275` 已有 `increment_access()` 在 recall 时递增
- `scoring.py:121-152` `recalculate_confidence()` 已用 access_signal（权重 0.1）

因此建议 2 从"新功能"降级为"参数调优 + 配置化"，工作量大幅降低。

## 3. 架构现状（探索结果）

### 3.1 Recall 评分机制（`src/carrymem/scoring.py`, `selection.py`）

```
calculate_importance() = confidence * type_weight * recency_factor * access_factor
  access_factor(n) = 1.0 + log(1+max(0,n)) * 0.1   # scoring.py:101-103

select_memories() ranking:
  final = imp*0.7 + rel*0.3 + type_boost + temporal/aggregation bonuses
  → MMR diversification → mandatory-types-first reordering
```

- `access_count`/`last_accessed_at` 已在 schema（`schema.py:36,39`），已索引
- `recall_engine.py:262-275` `increment_access()` 在 recall 时批量递增

### 3.2 classify_message 管道（`src/carrymem/engine.py`, `coordinators/classification_pipeline.py`）

```
process_message() → ClassificationPipeline.classify_with_defaults()
  classify() 串行: RuleMatcher → PatternAnalyzer → SemanticClassifier（短路）
  classify_with_defaults() 包装: noise filter + fail-closed default
```

- SemanticClassifier LLM prompt 只返回 `{memory_type, tier, confidence, reason}` — **无实体字段**
- `RuleMatcher._match_partial()` 用 token overlap — **无字符串相似度**
- **无实体提取/规范化层**

### 3.3 Prompt 构建（`src/carrymem/prompt.py`, `prompt_builder.py`）

```
build_context() 预算分配: 60% memories / 20% knowledge / 20% rules
  → select_memories() + build_prompt()
build_prompt() 桶化: Mandatory / Important / Context / Outdated → 注入完整 raw_text
```

- **无摘要层**：每个记忆注入完整 `raw_text`/`content`
- **无渐进式披露**：无 depth/tier 分级
- **现成 hook**：`RecallBudget.type_quotas` 已为 `session_summary: 3` 预留槽位（`scoring.py:47-58`）

### 3.4 存储层（`src/carrymem/adapters/sqlite/schema.py`, `crud.py`）

当前 `memories` 表已有：`access_count`, `importance_score`, `last_accessed_at`, `version`

**缺失字段**（需 v1.0 migration）：`summary`, `summary_level`, `entity_normalized`, `entity_id`, `entity_type`

## 4. 详细设计

### 4.1 建议一：实体规范化（Ontology-lite）— 新功能

#### 4.1.1 动机

当前 CarryMem 无实体提取/规范化。"用户偏好 REST API" 和 "用户喜欢 REST APIs" 会被当作两条独立记忆，导致 recall 碎片化、重复存储。cognee 的 Ontology 层（RDF/OWL + 80% cutoff 模糊匹配）解决了这个问题，但完整本体论过重。CarryMem 采用规则式轻量方案。

#### 4.1.2 设计

**新增模块**：`src/carrymem/layers/entity_normalizer.py`

```python
class EntityNormalizer:
    """规则式实体规范化（Ontology-lite）。

    使用 difflib.SequenceMatcher (ratio ≥ 0.8) 做模糊匹配，
    将表面形式不同的实体映射到规范形式。无需 LLM。
    """

    SIMILARITY_THRESHOLD = 0.8  # 借鉴 cognee 的 80% cutoff

    def normalize(self, text: str, namespace: str) -> NormalizeResult:
        """从文本提取实体并规范化。

        1. 规则式实体提取（名词短语 + 已知实体匹配）
        2. 对每个实体查 entity_aliases 表
        3. 若无精确匹配，用 SequenceMatcher 找 ≥0.8 的别名
        4. 返回规范形式 + 新别名（待持久化）
        """
```

**classify 管道集成**：在 `ClassificationPipeline.classify()` 中加第 4 层

```
classify() 串行: RuleMatcher → PatternAnalyzer → SemanticClassifier → EntityNormalizer
                                                                  ↑ 新增
```

EntityNormalizer 作为 post-classification hook，不参与短路决策，仅丰富 metadata。

**新增存储表**：`entity_aliases`

```sql
CREATE TABLE IF NOT EXISTS entity_aliases (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    canonical_form TEXT NOT NULL,      -- 规范形式 "REST API"
    alias_form TEXT NOT NULL,           -- 别名形式 "REST APIs"
    entity_type TEXT,                   -- "concept" / "tool" / "preference"
    namespace TEXT NOT NULL,
    similarity_score REAL DEFAULT 1.0,  -- 精确匹配=1.0, 模糊匹配<1.0
    created_at TEXT NOT NULL,
    UNIQUE(canonical_form, alias_form, namespace)
);
CREATE INDEX IF NOT EXISTS idx_entity_aliases_namespace ON entity_aliases(namespace);
CREATE INDEX IF NOT EXISTS idx_entity_aliases_canonical ON entity_aliases(canonical_form);
```

**memories 表新增字段**（v1.0 migration）：

```sql
ALTER TABLE memories ADD COLUMN entity_normalized TEXT;  -- JSON: [{"canonical": "REST API", "type": "concept"}]
ALTER TABLE memories ADD COLUMN entity_id TEXT;           -- 主实体 ID（用于跨记忆关联）
```

#### 4.1.3 API 变更

- `CarryMem.classify_and_remember()` 返回的 metadata 新增 `entities` 字段（可选，向后兼容）
- 新增 CLI：`carrymem entities list` / `carrymem entities merge <a> <b>`（手动合并规范形式）
- 新增 MCP 工具：`list_entities`（KNOWLEDGE 类，可选）

#### 4.1.4 向后兼容

- `entity_normalized`/`entity_id` 字段默认 NULL，现有记忆不受影响
- EntityNormalizer 可通过配置禁用：`CARRYMEM_ENTITY_NORMALIZATION=0`（缺省启用）
- classify 管道短路逻辑不变，EntityNormalizer 仅在分类完成后丰富 metadata

#### 4.1.5 测试策略

| 维度 | 测试 |
|------|------|
| Happy Path | "REST API" / "REST APIs" / "rest api" 归一化到同一规范形式 |
| 边界 | 空文本、无实体文本、超长文本 |
| 错误 | SequenceMatcher 异常、entity_aliases 表锁 |
| 性能 | 1000 实体规范化 < 200ms |
| 集成 | classify_and_remember → recall_memories 跨表面形式命中 |
| 安全 | 命名空间隔离，不跨用户规范化 |

#### 4.1.6 风险

| 风险 | 缓解 |
|------|------|
| 误合并（"Java" 语言 vs "Java" 咖啡） | 保留 `entity_type` 区分；提供手动 `entities merge/unmerge` CLI |
| 规则式提取精度不足 | 首版仅处理明显名词短语；后续可接 LLM 增强（可选） |
| 性能（大量别名模糊匹配） | 限制每次匹配候选集（按 namespace + 首字母索引） |

### 4.2 建议二：访问频率加权增强 — 参数调优（已存在）

#### 4.2.1 动机

`access_factor` 已存在但权重固定（`ACCESS_SCALE=0.1`，`recalculate_confidence` 中 access_signal 权重 0.1）。当前频繁访问的记忆与冷记忆区分度不足。

#### 4.2.2 设计

**参数配置化**：将硬编码的权重提取为可配置常量

```python
# scoring.py
ACCESS_SCALE = float(os.environ.get("CARRYMEM_ACCESS_SCALE", "0.1"))  # access_factor 对数斜率
ACCESS_SIGNAL_WEIGHT = float(os.environ.get("CARRYMEM_ACCESS_SIGNAL_WEIGHT", "0.1"))  # recalculate_confidence 中的权重
```

**selection.py 增强**：在 `select_memories()` 的 final-score 块增加访问频率 boost

```python
# selection.py:216-219 附近
access_boost = min(access_count * 0.01, 0.1)  # 上限 0.1，避免热记忆霸屏
final = imp * 0.7 + rel * 0.3 + type_boost + temporal_bonus + access_boost
```

#### 4.2.3 API 变更

无 API 变更。仅新增 2 个环境变量（缺省值与当前一致，向后兼容）。

#### 4.2.4 测试策略

| 维度 | 测试 |
|------|------|
| 配置 | 环境变量覆盖生效，缺省值与当前一致 |
| 评分 | access_count=0 vs 100 vs 1000 的 final score 差异在预期范围 |
| 回归 | 现有 recall 测试全绿（缺省值行为不变） |
| 性能 | 评分计算 < 1ms |

#### 4.2.5 风险

低。纯参数调优，缺省值保持向后兼容。

### 4.3 建议三：摘要层 + 渐进式披露 — 新功能（LLM 开关）

#### 4.3.1 动机

当前 `build_prompt()` 注入每个记忆的完整 `raw_text`，token 消耗高。codebase-memory-mcp 通过摘要+分级披露实现 120x token 节省。但 CarryMem 核心优势是"零 LLM 零依赖"，因此摘要层 LLM 缺省关闭，用规则式 fallback；用户可选开启 LLM 摘要（TRAE 本地环境自动打开）。

#### 4.3.2 LLM 开关策略（用户约束）

```
enable_llm_summary 配置优先级:
  1. 环境变量 CARRYMEM_LLM_SUMMARY=1/0  （最高优先级，显式覆盖）
  2. 配置文件 ~/.carrymem/config.yaml: summary.llm_enabled: true/false
  3. TRAE 环境检测: 若 CARRYMEM_ENV=trae 或 TRAE_SESSION_ID 存在 → 自动打开
  4. 缺省: False（保持零 LLM 优势）
```

**LLM 关闭时**：用规则式摘要（取首句 + 关键短语 + 类型标签）
**LLM 打开时**：调用 LLM 生成摘要（复用现有 `LLMBackend` 抽象）

#### 4.3.3 设计

**新增模块**：`src/carrymem/summary/`

```
src/carrymem/summary/
├── __init__.py
├── rule_based.py      # 规则式摘要（零 LLM）
├── llm_based.py       # LLM 摘要（可选）
├── progressive.py     # 渐进式披露
└── config.py          # LLM 开关配置
```

**4.3.3.1 摘要生成**

```python
# rule_based.py
class RuleBasedSummarizer:
    """零 LLM 摘要器。

    策略:
    - user_preference/correction: 取 raw_text 首句 + 类型标签
    - decision: 取 "决定:" 后内容
    - fact_declaration: 取原始声明
    - 其他: 取前 80 字符 + "..."
    """

    def summarize(self, memory: MemoryEntry, level: int = 1) -> str:
        """level 1=超短(标签+关键词), 2=短(首句), 3=完整"""

# llm_based.py
class LLMSummarizer:
    """LLM 摘要器（可选，需配置 API key）。"""

    def summarize(self, memory: MemoryEntry, level: int = 1) -> str:
        """调用 LLM 生成摘要，失败时降级到 RuleBasedSummarizer。"""
```

**4.3.3.2 渐进式披露**

```python
# progressive.py
class ProgressiveDiscloser:
    """根据预算和重要性分级披露记忆。

    深度层级:
    - depth=1 (超短): "[标签] 关键词" — 用于 Outdated 桶
    - depth=2 (短):   "[标签] 首句摘要" — 用于 Context 桶
    - depth=3 (完整): "[标签] 完整 raw_text" — 用于 Mandatory 桶（默认行为）
    """

    def render(self, memory: MemoryEntry, bucket: str, budget: int) -> str:
        """根据桶和剩余预算选择披露深度。"""
```

**4.3.3.3 prompt.py 集成**

修改 `build_prompt()`（`prompt.py:153-211`）：

```
当前: 每个桶注入完整 raw_text
增强: 根据 bucket + budget 选择 depth
  - Mandatory: depth=3 (完整) ← 保持当前行为
  - Important:  depth=2 (短摘要)
  - Context:    depth=2 (短摘要)
  - Outdated:   depth=1 (超短)
```

**4.3.3.4 摘要缓存**

`memories` 表新增字段（v1.0 migration）：

```sql
ALTER TABLE memories ADD COLUMN summary TEXT;           -- 缓存的摘要
ALTER TABLE memories ADD COLUMN summary_level INTEGER;  -- 摘要深度级别
```

摘要生成后缓存到 `summary` 字段，避免重复计算。`raw_text` 更新时清空 `summary`（失效）。

**4.3.3.5 现有 hook 复用**

`RecallBudget.type_quotas` 已为 `session_summary: 3` 预留槽位（`scoring.py:47-58`）。v0.5.0 启用此槽位：session_summary 类型记忆用摘要形式注入 prompt 头部。

#### 4.3.4 API 变更

- `build_prompt()` / `build_context()` 新增可选参数 `progressive: bool = False`（缺省关闭，向后兼容）
- 新增 `CarryMem.generate_summary(key: str, force: bool = False) -> str`（手动生成摘要）
- 新增环境变量：`CARRYMEM_LLM_SUMMARY`, `CARRYMEM_ENV`, `CARRYMEM_SUMMARY_MAX_BUDGET`

#### 4.3.5 向后兼容

- `progressive` 缺省 `False` — 不启用时行为与 v0.4.1 完全一致
- `summary`/`summary_level` 字段默认 NULL，现有记忆不受影响
- LLM 摘要器失败时自动降级到规则式（fail-safe）

#### 4.3.6 测试策略

| 维度 | 测试 |
|------|------|
| Happy Path | 规则式摘要生成 4 种类型各 1 例 |
| LLM 开关 | 环境变量覆盖、TRAE 环境检测、缺省关闭 |
| 渐进式 | 4 个桶的 depth 选择正确 |
| 预算 | token 预算耗尽时降级到更浅 depth |
| 缓存 | 摘要缓存命中、raw_text 更新后失效 |
| 降级 | LLM 摘要失败 → 规则式 fallback |
| 回归 | progressive=False 时行为与 v0.4.1 一致 |
| 性能 | 1000 记忆 progressive prompt < 500ms |

#### 4.3.7 风险

| 风险 | 缓解 |
|------|------|
| 规则式摘要质量不足 | 作为 LLM 关闭时的 fallback，用户可选开启 LLM |
| LLM 摘要延迟 | 缓存到 `summary` 字段；异步生成（非阻塞 prompt 构建） |
| 摘要丢失关键信息 | Mandatory 桶始终用 depth=3（完整）；摘要仅用于低优先级桶 |
| TRAE 环境误检测 | 多重信号验证（`CARRYMEM_ENV` + `TRAE_SESSION_ID`） |
