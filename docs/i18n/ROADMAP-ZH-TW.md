## 上下文工程洞察 (新增 — v0.2.8)

### Lost-in-the-Middle效應對規則注入的影響

LLM注意力遵循U型曲線：**開頭和結尾注意力高，中間注意力低**（10-40%召回率下降）。這直接影響規則注入的可靠性。

**當前問題** (v0.2.1-v0.2.7):
```
## 個人規則 (來自CarryMem)
規則A (relevance=0.92, override=true)   ← 開頭: 高注意力
規則B (relevance=0.88, override=false)  ← 中間: 注意力坍塌
規則C (relevance=0.85, override=true)   ← 中間: 最重要的規則被忽略！
規則D (relevance=0.80, avoid)           ← 結尾: 次要注意力
```

**v0.2.8解決方案**: 錨定佈局模式
```
## 個人規則 (來自CarryMem)

### 絕對禁止 (不可違反)
- [forbid] 絕不在未驗證的情況下引用競品資料     ← 頭部錨點

### 推薦行為
- [always] 漢堡倉庫需電話確認庫存
- [avoid] 跨境調撥優先使用國內倉庫

### 強制執行 (不可跳過)
- [always] 所有外部報價必須包含有效期           ← 尾部錨點
```

### 上下文預算監控

當規則注入超過上下文視窗70%時，自動壓縮：
- 優先權：保留override=true規則，將avoid規則壓縮為摘要
- 超閾值：每條規則一行摘要，不附帶來源資訊

### DDD語言視圖

CarryMem概念對應到DDD概念，實現與企業架構師的對話：

| CarryMem | DDD | 關係 |
|----------|-----|------|
| trigger | 限界上下文(Bounded Context) | 範圍定義 |
| rule_type (forbid/avoid/always) | 聚合一致性約束 | 不變量≈forbid, 保證≈always |
| override | 不變量(Invariant) | 不可被更高優先權覆蓋 |
| source_memories | 事件溯源鏈(Event Sourcing Chain) | 規則可追溯到原始經驗 |
| refine過程 | 統一語言精煉(Ubiquitous Language Refinement) | 具體→一般抽象 |

實作方式：`format_rules_as_prompt()` 中 `style="ddd"` 參數，僅顯示層，不改變儲存。

## 安全策略 (縱深防禦)

### 第1層: 輸入驗證 (v0.2.1 ✅)
- Prompt注入模式偵測 (10+模式)
- SQL注入字元阻斷
- 模板注入防護
- HTML/XSS標籤剝離
- 長度限制 (trigger: 200, action: 500)

### 第2層: 使用限制 (v0.2.1 ✅)
- 全域規則上限: 最多3個 trigger="*"
- 總規則上限: 最多200條
- 速率限制: 20/小時, 50/天

### 第3層: 自動晉升安全 (v0.2.5 ✅)
- 自動晉升需使用者明確操作
- 所有自動生成規則初始為 `override=false`
- 未確認候選7天過期
- 佇列大小限制 (50個待處理)

### 第4層: 經驗學習安全 (v0.2.6 ✅)
- 重複記憶偵測 (跳過已處理的)
- 消毒器驗證所有提取的trigger/action
- 所有經驗→規則操作有審計追蹤

### 第5層: 精煉安全 (v0.2.7 ✅)
- 每會話最多5輪
- 會話過期 (7天)
- 所有精煉規則經過消毒器

### 第6層: 上下文工程安全 (v0.2.8 規劃)
- 上下文預算監控防止提示溢出
- 錨定佈局確保關鍵規則不會丟失在中間
- 壓縮策略保留override=true規則
